# MI50 / gfx906 实验分支

项目 **strata-gfx906**，分支 `gfx906`：<https://github.com/webzone/strata-gfx906/tree/gfx906>。
基于上游 Strata 0.1.30 / `30ec18ec7094550fcc594fd948220d511d80464e`；
llama.cpp/ggml 固定 `3cf03257f219afbe7334045ff7c6a06ac68c627d`。

## 当前结论

**双 MI50 已实际运行 GSQ-RCO IQ2_XS 模型，生成和 MTP 可工作。** 不是上游 MI50 支持声明，
不等于生产就绪：目前只做短提示、4K context，未完成长上下文、长稳、全模型 CPU logits/layer parity、
真实工作负载速度对比或 API/服务部署。HIP 仍无图像支持、单请求串行。

T5810：Xeon E5-1650 v3 / AVX2（无 AVX-512）、121GiB RAM、2×MI50 实测每卡 31.984GiB，
`gfx906:sramecc+:xnack-` / 物理 wave64；Ubuntu 26.04.1、ROCm 7.2.4、AMD Clang 22。
SDK/驱动和调校/温控服务未改。依赖只装在本项目 `.venv`。

## 兼容性设计

- 默认 **OFF** 的 `STRATA_EXPERIMENTAL_GFX906`；安装器显式 `--experimental-gfx906`。
  使用真实 gfx906 code object，保留编译架构和物理 wave 检查，不设 `HSA_OVERRIDE_GFX_VERSION`。
- 物理 wave64 保留两个逻辑 wave32。ballot 依据 **线性 block thread index** 取正确半波，
  width-32 shuffle / reduction 保留。DP4A 用 gfx906 signed、non-saturating native dot4。
- MI50 profiling 的 `wall_clock64()` 为约 **25MHz**，换算 40ns；两卡主动 kernel 校准约
  24.997/24.996MHz。跨 CPU sleep 的空闲区间校准在本次测试未通过，改用 warmup 后主动 kernel；
  不把空闲/冷启动读数混成 profiling 频率。
- 多卡复用上游 **连续层 / pipeline split**，不是 tensor parallel。verify 使用 portable mapped
  pinned host buffer，在每个设备上单独取得 alias，生产者 stream 同步之后消费者才读取。
  `MappedHandoff` 管理完整 serve-loop 生命周期。prefill 是独立的 pinned 双缓冲 DMA 路径。
  两种交接都不要求开启 P2P。
- AMD GPU 列表保留顺序，如 `0,1` / `1,0`。显式配置清除冲突的父 `ROCR_VISIBLE_DEVICES` /
  `CUDA_VISIBLE_DEVICES`，再设 `HIP_VISIBLE_DEVICES`。RDNA 分支保留，但本机没有 RDNA 卡做回归。

## 构建和回归

只使用既有 **系统 ROCm 7 / HIP / hipBLAS**。没有 gfx906 的 RDNA TheRock wheel index，不能拿它顶替。

```bash
# 先准备上述 pinned llama.cpp 根目录（不是其 ggml/ 子目录）
# 本机使用 third_party/llama.cpp -> 既有隔离实验的 pinned checkout
cmake --preset hip-gfx906-multigpu
cmake --build --preset hip-gfx906-multigpu  # Release / portable AVX2 / MMQ / -j2
ctest --preset hip-gfx906-multigpu
.venv/bin/python -m unittest discover -s tests -p test_gfx906_setup.py
.venv/bin/python setup.py --check --backend hip --experimental-gfx906 --gpus 0,1
```

`hip-gfx906` 不要求双卡；`hip-gfx906-multigpu` 显式开启 `STRATA_HIP_MULTIGPU_TESTS`，
两张卡缺一即失败、不跳过。多卡测试会占用两卡，先查空闲状态，不停止现有工作负载腾卡。
`--check` 不迁移模型目录、不写 settings；这里没有运行安装器主流程。

测试包含波宽/intrinsics、KV、attention、GDN、router、MMQ、独立 CPU 算子 oracle 和多卡交接。
`hip_layer_handoff` 验证正向/反向、同设备切层、T=1/2/4/8、32 次 graph replay、
预填充 T=32/128/512 双缓冲和 guards，共 **137,980,416** 次精确检查；这是传输测试，不是模型 parity。
合成 oracle 覆盖 **9 种量化 / 33 组 MMVQ / 12 组完整专家**，其中包含实际模型的 IQ1_M / Q2_0 组合。
GEMM/MMQ 大输出检查有限性 + 64 点 double oracle，不是穷举每个输出。

最终 CTest **41项中40通过、1跳过、0失败**（46.10s）；Python入口/下载安全回归 **18/18**。
小型原始证据与汇总在 [gfx906-results/20261001](gfx906-results/20261001/README.md)，
可用 `python3 tools/gfx906_summary.py docs/gfx906-results/20261001` 重新核对。

preset **排除** `platform_memory_test`（普通用户 8MiB memlock）和历史 `ple_parity`（缺独立捕获 fixtures）。
`hip_prefill_hipblaslt_gemm` 在此硬件/配置跳过，不计为通过。没有改变 memlock、配置 hugetlb 或以 root 跑 GPU。
真实模型日志仍有 `mlock failed` / 4KB 页回退；CUDA/HIP 注册实际只锁约 7GiB，而非全专家 arena。

## 模型身份、存储和准备

主模型：`ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF`，revision
`ed59f92082b1e93c0e96d60a8b11aab089b52f09`。IQ2_XS 两分片 **68,026,093,024B**（68.03GB / 63.35GiB），
LFS SHA256 固定在 `tools/gfx906_model.py`，完整校验后才 rename `.part`。有目录锁、源身份、断点范围验证、
合计 40MiB/s 限速和 4GiB 系统盘安全底线；不覆盖冲突文件、不删除其他模型/镜像。

**IQ2_XS 文件名不是所有张量的类型**：96 个 gate/up 混合 IQ2_S（68）、IQ2_XXS（22）、IQ1_M（6）；
48 个 down 是 Q2_0。不能只验 IQ2_XS 算子，也不能强制 IQ1_M 走不支持它的 MMQ。

```bash
# 首次须核算峰值空间；工具默认只打印计划，--fetch 才下载
.venv/bin/python tools/gfx906_model.py --fetch --directory models/IQ2_XS
# 不加 --experts-bin：float/dense pack 约1.43GiB，专家从 GGUF 装入 RAM
.venv/bin/python tools/iq_pack.py \
  --gguf models/IQ2_XS/Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001-of-00002.gguf \
  --out packs/iq2_xs

# MTP 只取 checkpoint 的31个张量，共5,214,301,696B，不取整个checkpoint
.venv/bin/python tools/mtp_fetch.py inventory --out mtp/bf16
.venv/bin/python tools/mtp_fetch.py fetch --out mtp/bf16 --rate-mib 20
STRATA_GGUF_PY=third_party/llama.cpp/gguf-py .venv/bin/python tools/mtp_pack.py \
  --src mtp/bf16 --experts q2_0 --out mtp/mtp-q2_0.gguf
.venv/bin/python tools/mtp_rt.py --gguf mtp/mtp-q2_0.gguf --out mtp/rt
cp data/draft_vocab.bin mtp/rt/draft_vocab.bin
```

MTP 固定 checkpoint revision `de4b8e4d43b917e7706784d8bb445c9af86a3540`，校验 Range 响应/尺寸和 inventory revision。
它是按范围提取的 BF16 源张量（保存本地 hash），不是完整源 checkpoint 的 LFS SHA 校验。
原始 MTP 张量、量化 GGUF、runtime 均保留，合计约6.5GiB；runtime 在 GPU 上约794MiB（另有 draft head）。
**不产生额外约35.5GB的主模型 `experts.bin`**：已有路径把33.02GiB专家装入 RAM，双卡分别缓存
12,288 个专家（约16.19/16.83GiB）。初始约82.94GB free 足够这种准备路径；不是原先保守150GB全pack预算。
完成后根盘约 **5.7GiB free / 98%**，余量有限，下一步先检查 `df -h /`，不要自动删原始张量/权重。
重复验证已完整的源文件仅要求4GiB安全底线，不再次强求尚未准备时的pack/MTP预留。

## 真实生成复现（无HTTP）

先确认无正在运行的推理工作负载、GPU空闲、RAM足够、磁盘至少4GiB。
这些工具只操作 stdin/stdout，不启动浏览器、API listener 或恢复任何容器。
上游加载提示可能提到 browser；不表示工具真的开启HTTP。

```bash
# native pack仍需 --spec >=2 作为verifier窗口，但此CLI不加载/使用MTP
# 工具已带 --spec 2 --prefill 128，不能写 --spec 0
 timeout --kill-after=30s 1200 .venv/bin/python tools/gfx906_cli_baseline.py \
   --gpu 0 --out logs/cli-no-mtp.json
 timeout --kill-after=30s 1200 .venv/bin/python tools/gfx906_smoke.py \
   --gpus 0,1 --split 24 --min-p 0.5 --out logs/smoke-dual.json
# 对照：--gpus 0；反向：--gpus 1,0；阈值对照：--min-p 1
```

输出 JSON 保留 prompt/generated IDs、文本、退出状态、真实引擎时间和 MTP 统计；拒绝覆盖旧证据。
`min-p=1` 是阈值对照，仍加载/可能计算 MTP，不能称为无MTP性能基线。
初测双卡正确输出 `12`、`MI50 ready.`、Python `square(x)`；128-token数字序列 decoder统计
**128 / 7.1953s ≈17.8 tok/s**、过滤后所提96个draft全部接受、专家cache命中100%。
短提示首次读取约18–21 tok/s；这不代表长prompt MMQ吞吐。不是通用100%MTP接受率、不是60–95 tok/s，
也没有与不同权重的历史 llama.cpp/vLLM 数据作等条件比较。

**4个提示的全部生成token（每模式153个）**在单卡 `0`、双卡 `0,1`、反向 `1,0`、
双卡 `min-p=1` 阈值对照间逐值一致。无MTP CLI的算术3个token也一致。
独立固定版 llama.cpp **CPU-only `llama-completion`**、同一GGUF/同一23-token模板也输出 `12`，退出0；
只核对这一项文本，不是全模型logits oracle。该pin的工具叫 `llama-completion`，不是旧的 `llama-cli`。

| 128-token数字序列单次观测 | decoder tok/s | 专家cache命中 | 提出/接受draft |
|---|---:|---:|---:|
| 单MI50 + MTP | 16.1 | 77.1% | 96/96 |
| 双MI50 0,1 + MTP | 17.8 | 100% | 96/96 |
| 双MI50 1,0 + MTP | 17.9 | 100% | 96/96 |
| 双MI50 min-p=1 | 7.8 | 100% | 22/22 |

阈值1仍会提出22个draft，**绝不是MTP-off**。这些是冒烟观测，不是隔离的性能A/B：
部分轮次与CPU参考程序的编译重叠、自动cache容量也不同，不能用表格比值宣布多卡/投机速度倍率。
数字序列到46时因128-token上限截断，未声称完整写到50。
上游部分HIP日志沿用 `CUDA0/1` 名称；实际运行的是HIP gfx906，不是NVIDIA。

初轮测试错误保留：oracle注册误用不存在的 `gemm` mode，改为独立 `bf16` / `f16`；
时钟初测跨空闲CPU sleep，改为warmup后主动kernel校准；无MTP CLI初用 `--spec 0` 被上游native-pack门拒绝，
改为已有的 `--spec 2 --prefill 128` 路径。不能把这些失败删掉假装从未发生。

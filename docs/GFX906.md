Project **strata-gfx906**, branch `gfx906`: <https://github.com/webzone/strata-gfx906/tree/gfx906>.
Synchronized through upstream Strata **v0.1.37 / `db4f91a`**
with a merge commit on `gfx906`. The original port and archived GPU acceptance evidence used

`3cf03257f219afbe7334045ff7c6a06ac68c627d`.

This fork exists because upstream does not support MI50 / MI60 wave64. Future upstream updates
are absorbed through reviewed merges while preserving and optimizing the real gfx906 backend;
upstream wave32 support must not replace it. MI60 is an intended target, not yet independently tested.
After every upstream merge, update the source version at the top of `README.md` and its current
version/commit references in the same merge commit. Historical benchmark and deployment labels retain
the version actually measured; updating source is not new hardware validation.

## Current status

upstream MI50 support claim or production sign-off. The archived regression smoke tests cover short

new optional Linux CPU encoder is integrated but not hardware-validated on gfx906. Requests are serialized.

## Opt-in cold-prefill work — `gfx906-prefill-opt` (v0.1.37)

This development branch starts at `e2c88b4` on `gfx906`; it does **not** replace the deployed v0.1.34
engine or change its saved launchers/listener. The following are experimental compute paths; source-specific
bounded model measurements below are not general speed/quality guarantees. Both switches require the
real gfx906 experimental HIP build and default OFF:

| Switch | Candidate path / fallback |
|---|---|
| `STRATA_GFX906_PREFILL_ATTN=1` | INT8-KV QSA prefill, FP32 online softmax, one block per query/KV head; no WMMA, split-K partial writes or merge kernel. Reuses K/V across the 12 grouped heads, **not** across different query rows. Other architectures/geometries/KV formats retain the existing path. |
| `STRATA_GFX906_MTP_BATCH=1` | On a layer split, try the **last stage's** `Prefill::draft_kv()` with that card's scratch/stream; retain its device, scratch, KV-mode and `STRATA_MTP_BATCH=0` guards and token-window fallback. Single-GPU behavior is unchanged. |

Only the exact value `1` enables a new compute path. Keep `STRATA_EXPERIMENTAL_GFX906=ON`, compile for
`gfx906`, retain runtime architecture checks, and never use `HSA_OVERRIDE_GFX_VERSION`. INT8 KV and
expert quantization are unchanged. Native embedding additionally resolves/caches a separate mapped-host
alias on each consuming device, prepared before MTP graph capture; an owner-only VRAM fallback is refused
on another card rather than requiring P2P. Its immutable host table is fully populated before consumers run.
This alias change is a correctness fix, not a performance switch.

`STRATA_PREFILL_TIMING=1` now emits schema-1 `strata prefill profile:`, `draft:` and `request:` JSON
records on **stderr**, without changing the pipe protocol. Each stage has its device, layer range, position,
actual buffer chunk and invocation-local (not accumulated) stats. These cover QSA, GDN, expert computation,
MMQ/FP16/fused layer-chunk counts and FP16 fallback layer IDs, host grouping wait/planning, expert staging,
handoff, next-stage wait/drain, callbacks/MTP and request-level expert-cache refill. Existing human timing
lines remain available. The GPU `chunk tail` bucket includes handoff/callback/MTP and idle waits, including
the final tail (closed with an ending event). GPU timelines include stream waits; host durations overlap them. Next-stage wait
includes pipeline drain. **Do not sum stage wall times across GPUs or add overlapping timer categories.**
Request prefill timers stop before the first verify window: they are not TTFT or completed-generation tok/s.

## Compatibility design

- `STRATA_EXPERIMENTAL_GFX906` defaults **OFF**; the installer requires explicit
  `--experimental-gfx906`. The binary uses real gfx906 code objects and retains compiled-architecture
  and physical-wave checks. Do not set `HSA_OVERRIDE_GFX_VERSION`.
- Preserve two logical wave32 groups inside physical wave64. Choose the correct ballot half using the
  **linear block-thread index**; retain width-32 shuffle/reduction behavior. Use gfx906 signed,
  non-saturating native dot4 for DP4A.
- MI50 `wall_clock64()` profiling uses an approximately **25 MHz** counter (40 ns per tick). Active
  kernel calibration measured approximately 24.997/24.996 MHz on the two cards. An idle interval
  measured across CPU sleep was not a valid calibration; use a warmed, active kernel instead.
- Multi-GPU operation reuses upstream contiguous-layer **pipeline splitting**, not tensor parallelism.
  Verify handoff uses portable mapped pinned host memory, obtains a device alias separately on each
  participant, and synchronizes the producer before the consumer reads. `MappedHandoff` remains alive
  for the full serve loop. Prefill uses a separate pinned double-buffer DMA path. Neither path enables
  or requires P2P.
- AMD GPU order is preserved, e.g. `0,1` or `1,0`. For an explicit HIP selection, the child environment
  clears conflicting `ROCR_VISIBLE_DEVICES` / `CUDA_VISIBLE_DEVICES` masks and sets
  `HIP_VISIBLE_DEVICES`. RDNA paths remain, but no RDNA card was available for regression testing.

## Install, start, and stop on MI50

This port is specifically tuned to run **Qwen3.8-Flash-Next GGUF** model files. The model's native/trained
context length is **262,144 tokens**; shorter `--context` settings are runtime limits imposed for resource
reasons, not a different native model context. Full-length inference still requires workload and system
validation. The current gfx906 run has used IQ2_XS, but this is a tested quantization choice, not the only
one available; select other supported GGUF quantizations for the desired quality, speed, and hardware fit.

For a normal user install, run the repository's Linux setup script. It creates a project-local Python
environment, downloads the pinned llama.cpp source and selected model/MTP files, compiles the HIP engine
for the selected gfx906 card(s), and writes the serving config and launcher. A clean IQ2_XS install
needs roughly 80 GB or more of free disk space; requirements vary with model/quantization. Use `--data-dir`
for a larger volume if needed.

```bash
export STRATA_API_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"

./setup.sh \
  --backend hip \
  --experimental-gfx906 \
  --family qwen \
  --model IQ2_XS \
  --gpus 0,1 \
  --context 262144 \
  --kv int8 \
  --host 0.0.0.0 \
  --api-key "$STRATA_API_KEY" \
  --port 8095 \
  --yes \
  --no-start
```

`--gpus 0,1` selects both MI50 cards in the AMD device order shown by setup. Use `--gpu 0` for a
single card. Layer placement defaults to automatic; `--layer-split 24` is an optional explicit boundary
for the two-card layout used by the archived smoke test. The command selects the model's native
262,144-token context; reduce it only if available memory requires a lower runtime cap. Native context is
not a claim that the entire 262K range has completed acceptance testing. Omit `--no-start` to start the
model immediately after installation.

The example writes `strata-iq2_xs.json` and `run-iq2_xs.sh`. Start and stop it as follows:

```bash
./run-iq2_xs.sh
# Press Ctrl+C once in this terminal for a graceful stop.
```

The launcher runs in the foreground and opens the local web app after the model is ready. To start it
without opening a browser, run the server directly:

```bash
.venv/bin/python serve/server.py --engine strata \
  --config strata-iq2_xs.json --host 0.0.0.0 --port 8095
```

The generated config stores the API key, which is enforced when the server starts directly. On the
host, open `http://localhost:8095/`; from another device use the MI50 host's IP address and provide the
API key. Stop with Ctrl+C; a second Ctrl+C forces the engine to exit if graceful shutdown stalls. This
example binds to all interfaces, so always use a strong API key and suitable firewall restrictions; do
not publish the config file or key.

To change saved setup choices later, stop the server and rerun setup with `--setup`, for example. Set
`STRATA_API_KEY` to the same saved key first (or deliberately replace it and update clients):

```bash
./setup.sh --setup --backend hip --experimental-gfx906 --family qwen --model IQ2_XS --gpus 0,1 --context 262144 --kv int8 --host 0.0.0.0 --api-key "$STRATA_API_KEY" --port 8095 --yes --no-start
```

## Model identity, storage, and preparation

## Real generation smoke tests (no HTTP)

Before a model run, verify that no inference workload is using the GPUs, that RAM is available, and
that at least 4 GiB remain on disk. These helpers use stdin/stdout and do not start an API listener,
open a browser, or restore containers. An upstream engine message may mention a browser; the smoke
tools themselves do not open one.

```bash
# A native pack requires a verifier window (at least --spec 2), even without loading MTP.
# This CLI helper uses --spec 2 --prefill 128; do not set --spec 0.
timeout --kill-after=30s 1200 .venv/bin/python tools/gfx906_cli_baseline.py \
  --gpu 0 --out logs/cli-no-mtp.json

timeout --kill-after=30s 1200 .venv/bin/python tools/gfx906_smoke.py \
  --gpus 0,1 --split 24 --min-p 0.5 --out logs/smoke-dual.json
# Comparisons: --gpus 0; reverse order: --gpus 1,0; threshold comparison: --min-p 1.
```

JSON output preserves prompt/generated IDs, text, exit status, engine timings, and MTP counters; the
helpers refuse to overwrite existing evidence. `min-p=1` is a threshold comparison, not MTP-off: it
still loads and may compute MTP.

The initial dual-GPU smoke produced `12`, `MI50 ready.`, a Python `square(x)` function, and a number
sequence. For each of four prompts, all generated tokens matched exactly across single GPU `0`, dual
GPU `0,1`, reversed order `1,0`, and dual-GPU `min-p=1` modes (153 output tokens per mode). The no-MTP
single-GPU CLI arithmetic tokens also matched. Pinned CPU-only llama.cpp `llama-completion`, using the
same GGUF and the same 23-token prompt template, also returned `12` and exited successfully. This checks
one short answer only; it is not full-model CPU/logit parity. This llama.cpp pin's binary is named
`llama-completion`, not the older `llama-cli`.

## Remaining validation

The bounded v0.1.31 hardware checks and loopback deployment above are complete; the remaining goals are:

   production or connect this experimental engine to Home Assistant vision tasks.

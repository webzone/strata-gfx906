earlier names remain as symlinks, and the two deprecated text binaries are renamed `strata.DEPRECATED-20261006`

The owner measured the upstream path as faster on T5810. The fork text backend therefore stays in the
tree as history and as an emergency fallback. New deployments must not select it.

Two facts that caused the confusion, recorded so the next reader does not re-derive them:

- One switch name, `STRATA_EXPERIMENTAL_GFX906`, appeared in both the text path and the vision project.
  The vision project no longer requires it; `STRATA_VISION_HIP=ON` plus `CMAKE_HIP_ARCHITECTURES=gfx906`
  is enough there. The name still means the text backend in the main project and in `setup.py`.
- The text engine and the image encoder come from two CMake projects (`strata` and `strata_vision`), so
  they always need two build directories. One directory cannot produce both today.
After every upstream merge, update the source version at the top of `README.md` and its current
version/commit references in the same merge commit. Historical benchmark and deployment labels retain

## Experimental HIP vision on v0.1.39

Upstream v0.1.39's vision target enables only CUDA or CPU, and its installer declines `--vision gpu`
on AMD. This fork connects the **existing native HIP backend in the pinned llama.cpp/ggml** to mtmd;
it does not port the text engine's kernels into CLIP or replace the pinned dependency.
ggml already recognizes gfx906/GCN5 and physical wave64. This architecture has no native BF16
matrix instructions. The encoder expands BF16 vision weights **exactly to FP32 in memory** and uses
FP32 hipBLAS GEMMs. It reads the original pinned mmproj directly: no derived GGUF or extra download.
The separate HIP binary uses this expansion in its CPU mode too. The ordinary CPU-only build retains
upstream's BF16 activation arithmetic.

The initial direct HIP connection failed the predefined embedding thresholds (up to 8.4% relative L2).
Node captures identified BF16 activation rounding and CPU's FP16 GELU lookup versus GPU's analytic
GELU as precision differences. Two vision-only build-directory overlays expand the loader's BF16
tensors and emulate the CPU GELU's FP16 input/output rounding, including its +/-10 branches. They
leave the pinned checkout and the text engine unchanged. GPU GELU evaluates its formula rather than
copying the CPU lookup table, so small CPU/GPU differences remain. The encoder fixes the existing
`GGML_CUDA_CUBLAS_COMPUTE_TYPE` process variable to `f32` to prevent inherited precision overrides.

The new `STRATA_VISION_HIP` option defaults OFF. HIP vision requires Linux,
`STRATA_EXPERIMENTAL_GFX906=ON` and exactly `CMAKE_HIP_ARCHITECTURES=gfx906`; CUDA and HIP vision
cannot be enabled together. Runtime checks require an actual gfx906 card and the ROCm backend,
and select an explicit GPU backend instead of silently accepting a missing GPU as CPU encoding.
The CPU mode of the HIP binary hides both HIP and ROCR devices before backend initialization.
GPU warm-up failure aborts startup before `READY`.

The initial path uses ordinary GPU attention. Flash Attention, HIP graphs, VMM and MFMA MMQ are
disabled in this vision build. `--flash-attn on` is rejected for GPU use; `auto` selects `off`.
The standalone HIP encoder defaults to a 1,024 image-token cap if none is supplied. Image loading,
resizing and tokenization remain CPU work, as with upstream's CUDA encoder. The encoder is a
single-device process; it does not split CLIP tensors between GPUs or require P2P.

Build against the existing **unmodified** pinned llama.cpp source:

```bash
cmake -S tools/vision -B build-vision-hip -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DLLAMA_DIR="$PWD/third_party/llama.cpp" \
  -DSTRATA_VISION_HIP=ON -DSTRATA_VISION_CUDA=OFF \
  -DSTRATA_EXPERIMENTAL_GFX906=ON -DCMAKE_HIP_ARCHITECTURES=gfx906 \
  -DCMAKE_HIP_COMPILER=/opt/rocm/llvm/bin/clang++ \
  -DCMAKE_HIP_COMPILER_ROCM_ROOT=/opt/rocm -DCMAKE_PREFIX_PATH=/opt/rocm \
  -DSTRATA_PORTABLE=ON
cmake --build build-vision-hip --target strata-vision -j2
```

The installer accepts `--backend hip --experimental-gfx906 --vision gpu` when **every selected
card is gfx906**. Other AMD architectures retain the upstream CPU choice. Its separate HIP vision
build directory and mode-aware stamp prevent a CPU encoder from being reused for GPU requests,
or vice versa. Update/start preserve the saved GPU mode and rebuild changed encoder sources.

For a manually prepared config, point `vision.exe` to this binary, use `vision.gpu: true`, provide
`vision.mmproj` and the first text-model GGUF as `vision.model`, set `vision.max_tokens` explicitly,
and include `--vision` in the text engine's args. The server warms the encoder **before** loading the
text engine, so automatic expert-cache sizing observes its real VRAM allocation. A previously loaded
text engine may have already consumed that space. Use a stopped service and idle cards for changes.
The existing `vision.cuda_device` field also selects a physical HIP ordinal on AMD; otherwise the
encoder uses the first GPU in the config's ordered HIP mask. With batch slots enabled, GPU image
encoding waits for admitted generation requests to finish and blocks new admissions while it encodes.
Generation registration and the image gate share the FIFO, preventing an idle-check race. The batch
slots remain available for concurrent decoding; CPU image encoding does not require this drain.

Validation uses `tools/gfx906_vision_check.py`: it retains the raw photo and generated BMP inputs,
stdout/stderr, finite SVE1 outputs, grid dimensions and full embedding comparisons to the HIP binary's
CPU mode, with identical losslessly expanded FP32 weights and ordinary attention.
Its predefined acceptance thresholds are relative L2 <= 0.005 and minimum per-token cosine >= 0.999.
CPU and GPU use six threads and ordinary attention for this comparison; encoder speedups are not
text-model tok/s or a comparison with CPU Flash Attention. MI60 requires independent validation.

The [MI50 validation record](gfx906-results/20261005-vision-v0.1.39/README.md) retains measured results,
source identities, raw encoder output and the earlier failed comparison. At a 300-token cap, five
images passed on each MI50; GPU0's newspaper encoding took 202 ms versus 5,720 ms on the matching
CPU path (median of three). Relative L2 was at most 0.002182 and minimum token cosine at least
0.999720. This is **not upstream BF16 embedding parity**: the changed activation arithmetic differs
from its CPU embeddings by 0.62-3.52% relative L2 on these fixtures. Original CPU evidence is retained
separately. At a 300-token cap the encoder's post-warm-up GPU0 VRAM use was about 2.05 GiB.
An actual 1,024-token fixture passed on GPU0 in 1,204 ms (matching CPU: 38,408 ms,
one call each); the larger warm-up used about 3.08 GiB. With the real two-MI50 IQ2_XS
text engine, the newspaper prompt generated `MEN WALK ON MOON` with identical seven
token IDs for HIP, matching FP32 CPU and original BF16 CPU embeddings. This is one
short image smoke, not broad model parity or long-context acceptance. Port 8082 was
left unbound during that isolated validation; deployment settings and the owner's manual launchers
were not changed until the separately authorized IQ3_S deployment below.

`709fc4d2c34abbede8b17cb93a4a9571c931338339d3848691c5b59f156d8452`, wave64 reference build
`6c1386d3ad47df1d1352cf4128f2f87227b7f3f2f5d76465a7531b72753c673a`.

Three changes were needed to build the upstream path against ROCm 10 (AMD clang 23.0.0git; ROCm 7.2.4
ships AMD clang 22.0.0git):

1. `src/kernels/cuda/fused_gr.cu`: inside `#if defined(STRATA_HIP_GFX906)`, the opt-in
   `STRATA_GR_SPLIT` read ended in `return;` inside a function that returns `bool`. Clang 22 emits no
   diagnostic for that line; clang 23 makes it an error (`-Wreturn-mismatch`). It now returns `false`,
   the value the `STRATA_GR_V3` read above returns, because neither read writes the q8_1 images and the
   caller quantizes. The branch needs `STRATA_GR_SPLIT=1`, which the deployed configuration does not
   set, and the fork-path binary does not compile that block at all. No deployed behaviour changes.
2. `include/strata/platform/hip_compat/strata_hip.h`: the CUDA-to-HIP name map lacked
   `cudaStreamCreateWithPriority` and `cudaDeviceGetStreamPriorityRange`. `src/core/mtp.cpp` has used
   both since v0.1.40 for the high-priority verify stream. HIP declares the same two calls
   (`hipStreamCreateWithPriority(hipStream_t*, unsigned int, int)` and
   `hipDeviceGetStreamPriorityRange(int*, int*)`), and the call site passes two arguments, so the
   aliases are signature-compatible.
3. `CMakeLists.txt`: `src/core/vmm.cpp` (Elastic K/V, added upstream by `2fbe321`) selects its
   implementation from `STRATA_USE_HIP`. Only `cmake/hip_backend.cmake` defines that macro, so the
   gfx906 compat build took the CUDA driver-API branch and failed on `#include <cuda.h>`; ROCm 7.2.4
   and 10.0 both ship no `cuda.h`. The file now receives `STRATA_USE_HIP=1` as a source-file property,
   so it takes its own `#else` branch ("HIP: no virtual memory here; the elastic K/V stays off"). Eight
   other sources and two headers also gate on `STRATA_USE_HIP`, so a global definition would move them
   to the wave32 backend; the definition is deliberately limited to this one file. Elastic K/V stays off
   on gfx906, as before.

**Verified:** `rocminfo` reports gfx906; a `hipMalloc`/kernel/`hipMemcpy` program and a 512 cubed
rocBLAS sgemm against the ROCm 10 libraries passed (`status=0`, `mismatches=0/262144`); `ldd` on both
new binaries resolves `libamdhip64.so.7`, `librocblas.so.5`, `libhipblas.so.3`, `libhipblaslt.so.1` and
`libhsa-runtime64.so.1` to `/opt/rocm-10.0/core-10.0/lib`. hipBLASLt still has no gfx906 device payload
in 10.0, the same as in 7.2.4.

**Reproducible:** a clean rebuild (`cmake --build <dir> --clean-first`) of both build directories from
`5c974a0` reproduced both SHA256 values exactly (`780661d4…` and `709fc4d2…`). Build logs:
`logs/rocm10-rebuild-5c974a0/`. The binaries the cutover script points at are therefore the ones this
commit produces on this machine.

**Not verified:** no real model was loaded with the ROCm 10 binaries. Both cards were full
(32.44/34.34 GiB and 33.58/34.34 GiB), so the new engine could not run beside the live service, and the
service was not stopped. No speed or output-quality comparison against the deployed ROCm 7.2.4 binary
was made. The 8082 cutover is a separate operator action and is still pending.

  **linear block-thread index**; retain width-32 shuffle/reduction behavior. Use gfx906 signed,
  non-saturating native dot4 for DP4A.
- MI50 `wall_clock64()` profiling uses an approximately **25 MHz** counter (40 ns per tick). Active
  kernel calibration measured approximately 24.997/24.996 MHz on the two cards. An idle interval
  measured across CPU sleep was not a valid calibration; use a warmed, active kernel instead.
- Multi-GPU operation reuses upstream contiguous-layer **pipeline splitting**, not tensor parallelism.
  Verify handoff uses portable mapped pinned host memory, obtains a device alias separately on each
  participant, and synchronizes the producer before the consumer reads. `MappedHandoff` remains alive
  for the full serve loop. Prefill uses a separate pinned double-buffer DMA path. Neither path enables
  or requires P2P.
- AMD GPU order is preserved, e.g. `0,1` or `1,0`. For an explicit HIP selection, the child environment
  clears conflicting `ROCR_VISIBLE_DEVICES` / `CUDA_VISIBLE_DEVICES` masks and sets
  `HIP_VISIBLE_DEVICES`. RDNA paths remain, but no RDNA card was available for regression testing.

## Install, start, and stop on MI50

This port is specifically tuned to run **Qwen3.8-Flash-Next GGUF** model files. The model's native/trained
context length is **262,144 tokens**; shorter `--context` settings are runtime limits imposed for resource
reasons, not a different native model context. Full-length inference still requires workload and system
validation. The current gfx906 run has used IQ2_XS, but this is a tested quantization choice, not the only
one available; select other supported GGUF quantizations for the desired quality, speed, and hardware fit.

For a normal user install, run the repository's Linux setup script. It creates a project-local Python
environment, downloads the pinned llama.cpp source and selected model/MTP files, compiles the HIP engine
for the selected gfx906 card(s), and writes the serving config and launcher. A clean IQ2_XS install
needs roughly 80 GB or more of free disk space; requirements vary with model/quantization. Use `--data-dir`
for a larger volume if needed.

```bash
export STRATA_API_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"

./setup.sh \
  --backend hip \
  --experimental-gfx906 \
  --family qwen \
  --model IQ2_XS \
  --gpus 0,1 \
  --context 262144 \
  --kv int8 \
  --host 0.0.0.0 \
  --api-key "$STRATA_API_KEY" \
  --port 8095 \
  --yes \
  --no-start
```

`--gpus 0,1` selects both MI50 cards in the AMD device order shown by setup. Use `--gpu 0` for a
single card. Layer placement defaults to automatic; `--layer-split 24` is an optional explicit boundary
for the two-card layout used by the archived smoke test. The command selects the model's native
262,144-token context; reduce it only if available memory requires a lower runtime cap. Native context is
not a claim that the entire 262K range has completed acceptance testing. Omit `--no-start` to start the
model immediately after installation.

The example writes `strata-iq2_xs.json` and `run-iq2_xs.sh`. Start and stop it as follows:

```bash
./run-iq2_xs.sh
# Press Ctrl+C once in this terminal for a graceful stop.
```

The launcher runs in the foreground and opens the local web app after the model is ready. To start it
without opening a browser, run the server directly:

```bash
.venv/bin/python serve/server.py --engine strata \
  --config strata-iq2_xs.json --host 0.0.0.0 --port 8095
```

The generated config stores the API key, which is enforced when the server starts directly. On the
host, open `http://localhost:8095/`; from another device use the MI50 host's IP address and provide the
API key. Stop with Ctrl+C; a second Ctrl+C forces the engine to exit if graceful shutdown stalls. This
example binds to all interfaces, so always use a strong API key and suitable firewall restrictions; do
not publish the config file or key.

To change saved setup choices later, stop the server and rerun setup with `--setup`, for example. Set
`STRATA_API_KEY` to the same saved key first (or deliberately replace it and update clients):

```bash
./setup.sh --setup --backend hip --experimental-gfx906 --family qwen --model IQ2_XS --gpus 0,1 --context 262144 --kv int8 --host 0.0.0.0 --api-key "$STRATA_API_KEY" --port 8095 --yes --no-start
```

The README's [startup and tuning options](../README.md#startup-and-tuning-options) section explains
setup flags, server flags, engine `args`, and which settings do not increase request concurrency.

### Runtime environment in JSON

Merge [the runtime environment example](../configs/gfx906-runtime-env.example.json) into an existing
model config; it is a fragment, not a complete model installation. Preserve its `exe`, `args`,
`tokenizer`, library directories, API key, and other environment entries. The engine inherits the
server's environment, then the config's `env` overrides matching variables. For HIP, the config's
`gpu` list owns `HIP_VISIBLE_DEVICES`; `[0, 1]` selects both cards in that order.

`GPU_MAX_HW_QUEUES=8`, `HSA_ENABLE_SDMA=0`, and `HSA_FORCE_FINE_GRAIN_PCIE=1` are requested runtime
experiments, not required gfx906 compatibility flags or proven performance improvements. Compare
with the default runtime before attributing any benefit. Never add `HSA_OVERRIDE_GFX_VERSION`;
remove it from the config and clear an inherited value when starting the launcher:

```bash
env -u HSA_OVERRIDE_GFX_VERSION ./run-iq2_xs.sh
```

`LLAMA_ENABLE_MTP_OPT`, `E_CUSTOM_AR`, and `GGML_TP_AR_NO_GATE` have no consumers in this Strata
engine or its pinned ggml source. MTP is controlled by engine arguments such as `--mtp` and `--spec`;
multi-GPU inference uses layer/pipeline splitting, not tensor-parallel custom all-reduce.
Generated `run-*.json` configs, like `strata-*.json`, stay untracked because they can contain secrets
and host-specific paths. Editing `env` requires a server/engine restart to take effect.

## Model identity, storage, and preparation

Main model: `ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF`, revision
`ed59f92082b1e93c0e96d60a8b11aab089b52f09`. The two IQ2_XS shards total **68,026,093,024 bytes**
(68.03 GB / 63.35 GiB). Their LFS SHA256 hashes are pinned in `tools/gfx906_model.py`; files are
renamed from `.part` only after full verification. The downloader uses a directory lock, source identity,
validated range resume, a 40 MiB/s aggregate rate limit, and a 4 GiB free-space floor. It will not
overwrite conflicting files or delete other models/images.

**The IQ2_XS filename does not describe every tensor.** The 96 gate/up expert tensors mix IQ2_S (68),
IQ2_XXS (22), and IQ1_M (6); the 48 down tensors use Q2_0. Do not validate only IQ2_XS kernels or
force IQ1_M through unsupported MMQ.

```bash
# First inspect the storage plan; --fetch is the explicit download action.
.venv/bin/python tools/gfx906_model.py --fetch --directory models/IQ2_XS

# Do not add --experts-bin: the ~1.43 GiB dense pack is created; experts are read from the GGUF into RAM.
.venv/bin/python tools/iq_pack.py \
  --gguf models/IQ2_XS/Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001-of-00002.gguf \
  --out packs/iq2_xs

# Fetch only the 31 MTP checkpoint tensors (5,214,301,696 bytes), not the whole checkpoint.
.venv/bin/python tools/mtp_fetch.py inventory --out mtp/bf16
.venv/bin/python tools/mtp_fetch.py fetch --out mtp/bf16 --rate-mib 20
STRATA_GGUF_PY=third_party/llama.cpp/gguf-py .venv/bin/python tools/mtp_pack.py \
  --src mtp/bf16 --experts q2_0 --out mtp/mtp-q2_0.gguf
.venv/bin/python tools/mtp_rt.py --gguf mtp/mtp-q2_0.gguf --out mtp/rt
cp data/draft_vocab.bin mtp/rt/draft_vocab.bin
```

MTP checkpoint revision: `de4b8e4d43b917e7706784d8bb445c9af86a3540`. Fetch validates HTTP ranges,
expected sizes, and inventory revision. The selected BF16 source tensors are range-fetched and locally
hashed; this does not claim a full-checkpoint LFS SHA256 verification. Source tensors, quantized GGUF,
and runtime outputs were retained and occupy about 6.5 GiB; the runtime uses about 794 MiB of GPU
memory, plus the draft head.

This preparation path does **not** write a duplicate ~35.5 GB main-model `experts.bin`: the existing
resident-from-GGUF path loaded 33.02 GiB of experts into RAM. Each GPU cached 12,288 experts
(approximately 16.19/16.83 GiB). About 82.94 GB was initially free, sufficient for this path; it is
not the earlier conservative 150 GB estimate for a full-pack layout. After preparation, the root disk
had about **5.7 GiB free / 98% used**. Check `df -h /` before any further writes; retain the source data
and do not delete unrelated files. Rechecking already complete source files requires the 4 GiB safety
floor, not the initial pack/MTP planning reserve.

## Real generation smoke tests (no HTTP)

Before a model run, verify that no inference workload is using the GPUs, that RAM is available, and
that at least 4 GiB remain on disk. These helpers use stdin/stdout and do not start an API listener,
open a browser, or restore containers. An upstream engine message may mention a browser; the smoke
tools themselves do not open one.

```bash
# A native pack requires a verifier window (at least --spec 2), even without loading MTP.
# This CLI helper uses --spec 2 --prefill 128; do not set --spec 0.
timeout --kill-after=30s 1200 .venv/bin/python tools/gfx906_cli_baseline.py \
  --gpu 0 --out logs/cli-no-mtp.json

timeout --kill-after=30s 1200 .venv/bin/python tools/gfx906_smoke.py \
  --gpus 0,1 --split 24 --min-p 0.5 --out logs/smoke-dual.json
# Comparisons: --gpus 0; reverse order: --gpus 1,0; threshold comparison: --min-p 1.
```

JSON output preserves prompt/generated IDs, text, exit status, engine timings, and MTP counters; the
helpers refuse to overwrite existing evidence. `min-p=1` is a threshold comparison, not MTP-off: it
still loads and may compute MTP.

The initial dual-GPU smoke produced `12`, `MI50 ready.`, a Python `square(x)` function, and a number
sequence. For each of four prompts, all generated tokens matched exactly across single GPU `0`, dual
GPU `0,1`, reversed order `1,0`, and dual-GPU `min-p=1` modes (153 output tokens per mode). The no-MTP
single-GPU CLI arithmetic tokens also matched. Pinned CPU-only llama.cpp `llama-completion`, using the
same GGUF and the same 23-token prompt template, also returned `12` and exited successfully. This checks
one short answer only; it is not full-model CPU/logit parity. This llama.cpp pin's binary is named
`llama-completion`, not the older `llama-cli`.

The following historical table is a one-shot 128-token number-sequence smoke test, not the recent
long-input/cache-assisted operating summary above and not a controlled performance comparison.

| One 128-token number-sequence observation | Decode tok/s | Expert-cache hit rate | Drafts offered/accepted |
|---|---:|---:|---:|
| One MI50 + MTP | 16.1 | 77.1% | 96/96 |
| Two MI50s, 0 then 1 + MTP | 17.8 | 100% | 96/96 |
| Two MI50s, 1 then 0 + MTP | 17.9 | 100% | 96/96 |
| Two MI50s, `min-p=1` | 7.8 | 100% | 22/22 |

The threshold comparison still offered 22 drafts; it is **not MTP-off**. These are a few smoke-test
observations, not an isolated performance A/B. Some runs overlapped CPU-reference compilation and
automatic cache capacities differed. Do not infer a general multi-GPU or speculative-decoding speedup
from these values. The number sequence stopped at 46 when its 128-token limit was reached; it did not
complete the requested 1–50 sequence. Some upstream HIP log messages retain `CUDA0/1` labels; these
runs used HIP gfx906, not NVIDIA GPUs.

Initial test failures are retained in the evidence set: an oracle was registered with a nonexistent
`gemm` mode and corrected to separate `bf16`/`f16` modes; clock calibration across an idle CPU sleep
was unsuitable and changed to a warmed active kernel; and the native-pack CLI rejected `--spec 0`, so
the no-MTP check was rerun using `--spec 2 --prefill 128`. Do not present these as if they never
occurred.
